# Thermal management

How the benchmark suite keeps a measurement honest on a machine that throttles, what the operating system will and will not tell you about heat, and the ways this was got wrong first.

> **Written 2026-08-28**, prompted by an M5 Max that throttles under sustained GPU load where the M4 Max the rest of these notes were taken on did not visibly do so.
> The strategy is not specific to that machine; the pitfalls are the useful part.

## Why a benchmark has to care

Every wrong answer in this project's history came from a contaminated pair, and heat is a contaminant the existing gate could not see.
The suite already refused to run on a loaded machine, but a throttled machine is not a loaded one: it is idle by every measure the harness took, and the only symptom is that the silicon runs slower.
A pair timed in that state measures the temperature as much as the path under test.

The exposure is structural rather than incidental.
The matrix is hours of back-to-back proving with a cooldown nowhere in it, which is the definition of sustained load, and the arm that heats the machine most is the one whose advantage is being claimed.
Throttling therefore biases the result in the direction that flatters nothing: it makes the GPU arm look worse, and it does so most on exactly the large workloads where the advantage is largest.

## What the machine will tell you

Most of the obvious sources are useless on Apple Silicon, which is worth writing down so that nobody spends the afternoon rediscovering it.

- **The load average is a phantom.** It reads over 20 on an idle machine and has no relationship to anything. This was already known and is recorded in [2026-08-24-benchmark-status.md](2026-08-24-benchmark-status.md); it is repeated here because it is the first thing anyone reaches for.
- **`pmset -g therm` reports nothing.** It answers "No thermal warning level has been recorded" on a machine that has been proving for hours, and `pmset -g thermlog` prints no output at all.
- **There are no thermal `sysctl` keys.** The `machdep.xcpm` tree that carried them on Intel does not exist here.
- **`powermetrics` needs root.** It is the only route to actual die temperatures and GPU residency, and requiring a password makes it unusable from an unattended overnight run.
- **`ProcessInfo.thermalState` works, unprivileged, and is the right signal.** It reports one of `nominal`, `fair`, `serious` or `critical`, and it is the same signal the system uses to tell applications to back off. Reading it needs three lines of Swift, which is what [`tools/thermal_state.swift`](../tools/thermal_state.swift) is; the suite compiles it on demand rather than committing a binary.

Note what this signal is and is not.
It is the operating system's own judgement about whether software should reduce its demands, which is exactly the question a benchmark harness wants answered.
It is not a temperature, it is coarse, and it lags: by the time it reads `serious` the throttling has already happened.
That is why the suite does not rely on it alone.

## What the suite does

Three measures, in order of how much they matter.

- **A pause after every run, proportional to that run's wall clock** — a quarter of it, floored at five seconds and capped at two minutes. Proportionality is the whole idea: heat is roughly proportional to the work that produced it, so a fixed pause is either pointless after a three-second proof or ruinous after a three-hundred-second one. This is the protection that does not depend on being able to read anything.
- **The pause is extended while the system reports pressure**, up to ten further minutes, so a machine that is genuinely hot is waited out rather than merely counted to.
- **Every run records the conditions it was taken under** — thermal state before and after, reclaimable memory, seconds cooled — so that a figure which looks wrong in six months can be checked against the state of the machine instead of guessed at. This is worth more than the gating, because gating can only prevent the runs it anticipates while a record explains the ones it did not.

The idle gate also now waits on reclaimable memory, which is a related failure for the same reason: the largest guests peak above a hundred gigabytes resident, and a run started before its predecessor has handed its pages back will swap, which measures the swap.

## Pitfalls

**Gating that lives in one script protects only that script.**
This is the one that cost a machine.
The cooldown and the thermal gate were written into the suite, and then the shader cache was warmed by a *separate* script that ran twenty-two guests back to back with none of it — and the machine took a watchdog panic partway through the heaviest guest in the suite, with twelve of eighteen cores offline.
The protection was real, correct, and in the wrong file.
Anything that drives the prover in a loop needs the same treatment as the suite, and the warming pass needs it most, because compiling and proving together is the hottest thing this repository does.

**Warm-up runs are hotter than measured ones, and are easy to forget.**
The discarded warm-up before each point is the run that compiles, so it is the run that heats the machine, and it used to be the one run with no pause after it.

**A cold shader cache looks exactly like throttling.**
Both present as a Metal arm that is slower than it should be for no visible reason, and confusing them sends you to the wrong fix.
Tell them apart by the kernel count rather than the clock: the host reports how many rounds took the CPU while a kernel was still compiling, and a cold cache says hundreds where a warm one says none.
See [2026-08-21-measurements.md](2026-08-21-measurements.md) and the compile-budget material in [USING.md](../USING.md).

**Compiling is CPU load, not GPU load.**
A long warming pass pins one core in the Metal compiler service and barely touches the GPU, so a thermal strategy tuned only to GPU work will not anticipate it.

**Waiting on the wrong pattern never finishes.**
A `pgrep -f` waiter matches its own command line, so a shell waiting for a prover to exit can wait forever on itself; this was already recorded in [2026-08-24-benchmark-status.md](2026-08-24-benchmark-status.md) and it bites again as soon as cooldowns make people write wait loops.

**A panic clears the scratch directory but not the shader cache.**
Losing a machine mid-run costs the logs written under the system temporary directory and nothing else: the compiled kernels survive a reboot, so the expensive part of a warming pass does not have to be paid twice.
Check by proving one small workload and reading the dispatch count before assuming the work is gone.

## What a full run recorded, and what it got wrong

> **Added 2026-08-28**, from the first complete matrix run under this pacing.
> The strategy above is what the run started with; the numbers here are why the pause is now a whole run's wall clock rather than a quarter of one, and why `nominal` is now waited for rather than merely recorded.

Three tiers, 714 timed runs, and the thermal reading was taken before and after every one of them.

| tier       | nominal | fair | points with runs in both states | fair/nominal wall, median |
| ---------- | ------- | ---- | ------------------------------- | ------------------------- |
| `standard` | 81      | 123  | 16                              | 1.010                     |
| `full`     | 90      | 270  | 19                              | 1.009                     |
| `apps`     | 8       | 136  | 3                               | 0.999                     |

Nothing ever reached `serious` or `critical`, the pauses were taken as designed, and read on its own that table says the pacing worked.
It did not, and the way it fails is the most useful thing in this document.

**`fair` is not one state.**
It spans everything from mildly warm to throttling hard, so the fair-against-nominal comparison only measures the distance between "cool" and "the average of everything above cool", which is small.
A tier that never leaves `fair` has no cool runs to compare against and its contamination is invisible: the `apps` tier read `fair` for 136 of 144 runs and looked, by every signal the harness recorded, exactly like the two tiers that were nearly clean.

**The only control that works is re-measuring on a machine that is actually cool.**
Four points from the `apps` tier, re-taken hours later with the machine idle and reading `nominal`:

- `eth-ecrecover/small`, CPU arm — 19.90 s in the tier, **14.31 s** cool. The tier was 39% slow.
- `eth-mpt/large`, CPU arm — 50.10 s in the tier, **39.62 s** cool. 26% slow.
- `eth-mpt/large`, GPU arm — 19.34 s in the tier, **14.32 s** cool. 35% slow.
- `eth-ecrecover/small`, GPU arm — 4.02 s in the tier, **3.91 s** cool. 3% slow.

**The two arms are not affected equally, so the errors do not cancel.**
This is what makes thermal contamination worse than noise.
The CPU arm uses every core and heats the machine hardest, so it loses most, and the ratio the benchmark exists to report moves in whichever direction the pair happens to be hurt unevenly: `eth-ecrecover/small` was inflated from a true 3.66x to a reported 4.96x, while `eth-mpt/large` was deflated from 2.77x to 2.59x.
A contaminated tier does not read as noisy. It reads as a finding.

**Heat accumulates across a sequence, not within a run.**
The pause was a quarter of the previous run's wall clock, which is generous after one proof and nothing at all after three hours of them.
The short guests suffered most, because a five-second pause after a fifteen-second proof does not undo the heat of the heavy guest that ran before it.
Even in the deliberately gentle re-measurement — ninety-second gaps around forty-second runs, reading `nominal` throughout — the three repeats still drifted from 38.0 s to 41.2 s.

**What changed as a result.**
The pause is now the whole of the previous run's wall clock, capped at five minutes, and the idle gate additionally waits for the thermal reading to return to `nominal` before any timed run, giving up after ten minutes and recording that it did.
Waiting for `nominal` is the part that matters: it is the only reading that means cool, where `fair` means only "not yet alarming".

**The ratio survives what the wall clock does not.**
The two microbenchmark tiers were spot-checked the same way, three points re-taken cool, and they came back with absolute times up to a tenth slow -- `bits/large` on the GPU arm read 14.45 s in the full tier against 13.06 s cool -- while the speedups those times produce were within 4.5% throughout:

| point            | cool  | standard tier   | full tier       |
| ---------------- | ----- | --------------- | --------------- |
| fib/standard     | 5.54x | 5.79x (+4.5%)   | 5.45x (-1.6%)   |
| bits/large       | 6.06x | 5.91x (-2.4%)   | 5.97x (-1.4%)   |
| sha256/standard  | 4.03x | 3.96x (-1.7%)   | 3.99x (-0.8%)   |

Mild heat warms both arms together and largely cancels in the ratio, which is why those tiers stand and the application tier does not.
What ruins a ratio is heat severe enough to hurt the arms *unequally*, and that is what three hours of the heaviest guests produced: 39% on one CPU arm against 3% on its GPU arm.
So the quantity being reported decides how much heat is tolerable, and a suite reporting ratios can survive conditions that would invalidate one reporting wall clocks -- up to a point, and that point is somewhere below where the application tier was run.

**And the check to run afterwards is not the one in the section above.**
Comparing `fair` against `nominal` within a tier is worth having and is nearly free, but it answers a weaker question than it appears to, and it will pass a tier that is uniformly ruined.
Re-measure two or three points cold, hours later, and compare against what was recorded.
If they agree the run can be read as taken; if they do not, no amount of caveat rescues it and the tier has to be run again.

## What a run under the cool regime looks like

The application tier re-run on 2026-08-28 is the reference for what the pauses buy.
All 144 runs began at `nominal`, and 1.84 hours of proving cost 2.22 hours of waiting — 1.0x of each run's wall clock in cooldown, plus 0.19 hours held at the gate waiting for `nominal` to come back.
Budget rather more than double the prover time for any tier run this way.

**The gate cannot keep a long run cool, only start it cool.**
Twenty-eight runs finished at `fair`, and twenty-seven of them were CPU-arm: every one of the eighteen CPU runs of `eth-pairing-check` and `eth-bls-verify`, which take four to five minutes on all cores.
The GPU arm never once ended `fair` at those sizes, because it finishes in a third of the time and leaves most of the machine idle while it runs.

This is not a harness failure and no pause length fixes it — a four-minute all-core proof heats the machine by itself, and a laptop has no cool version of that number.
It does mean the arms are not symmetric for the longest guests: the CPU arm is measured partly throttled and the GPU arm is not, so the multipliers for those two guests are flattered by whatever the CPU arm's own heat cost it.
Quote them as what a user gets, not as a ratio against a CPU that stays cool.

The asymmetry runs the *opposite* way from the one that ruined the first attempt, where the pauses were too short and both arms started hot.
That is worth keeping in mind when reading a multiplier: too little cooling and the CPU arm is hurt more because it runs longer under a machine that never recovers; enough cooling and the CPU arm is still hurt more, because it runs longer.
Heat never favours the CPU arm, so a Metal multiplier measured on a laptop is an upper bound in both regimes.

## Checking a finished run

The point of recording conditions is to be able to ask, afterwards, whether they mattered.
The check that answers it compares runs of the *same* point taken under different thermal states, which controls for everything except the heat:

```sh
python3 - <<'PY'
import json, glob, statistics as st
from collections import defaultdict
by = defaultdict(lambda: defaultdict(list))
for f in glob.glob("results/*-bench-*.jsonl"):
    for line in open(f):
        r = json.loads(line)
        if r.get("kind") == "meta" or r.get("warmup") or not r.get("verified"):
            continue
        k = (r["guest"], r["size"], r["config"], r["mode"], r["shard_size"], r["arm"])
        by[k][r.get("thermal_before")].append(r["wall_s"])
ratios = [st.median(d["fair"]) / st.median(d["nominal"])
          for d in by.values() if d.get("fair") and d.get("nominal")]
print(len(ratios), "points measured under both states")
if ratios:
    print(f"fair/nominal wall: median {st.median(ratios):.3f}, "
          f"range {min(ratios):.3f}-{max(ratios):.3f}")
PY
```

A median near 1.00 says the pauses held the machine below the point where heat changes the answer, and the run can be read as taken.
A median meaningfully above 1.00 says the cooldown was not enough and the figures are depressed by an unknown amount, which is a reason to re-run rather than to caveat.
